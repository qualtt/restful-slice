### Отчет о проектировании и реализации сервиса Slicer Worker

**Цель:** Создание воркера для асинхронной нарезки 3D-моделей, интегрированного с RabbitMQ и MinIO.

#### Шаг 1. Выбор архитектурного подхода (Sidecar паттерн)
На начальном этапе решался вопрос интеграции готового решения `orca-slicer-api` (написанного на Node.js). 
Вместо форка и доработки чужого кода (что усложнило бы поддержку и обновление будущем), был выбран паттерн **Sidecar**. 
Мы разворачиваем оригинальный контейнер `orca-slicer-api` без изменений, а рядом (в одной сети) поднимаем наш собственный легковесный контейнер-адаптер. Адаптер берет на себя всю работу с инфраструктурой (RabbitMQ, MinIO) и общается со слайсером по внутреннему HTTP.

#### Шаг 2. Анализ профилей и изменение AsyncAPI контракта
При анализе Dockerfile `orca-slicer-api` выяснилось, что профили сохраняются в эфемерную папку `/app/data`. Хранение профилей (пресетов) внутри контейнера или базы данных воркера сделало бы систему stateful и сильно усложнило бы синхронизацию при масштабировании до нескольких воркеров.

Было принято решение сделать воркер полностью **stateless**. Единым источником истины для профилей назначен MinIO. Order Service теперь сам определяет нужные файлы и передает воркеру прямые пути. В связи с этим был изменен AsyncAPI контракт:

```yaml
    SliceRequestedPayload:
      type: object
      additionalProperties: false
      required: [order_id, customer_id, minio_paths]
      properties:
        order_id: { type: string, format: uuid }
        customer_id: { type: string, format: uuid }
        priority:
          type: string
          default: normal
          enum: [low, normal, high]
        minio_paths:
          type: object
          additionalProperties: false
          required: [stl_file, printer_profile, process_profile, filament_profile]
          properties:
            stl_file: 
              type: string
              example: "stl/orders/3f8a6aef/model.stl"
            printer_profile: 
              type: string
              example: "profiles/printers/prusa_mk3s.json"
            process_profile: 
              type: string
              example: "profiles/process/0_20mm_quality.json"
            filament_profile: 
              type: string
              example: "profiles/filaments/generic_pla.json"
```

#### Шаг 3. Оптимизация получения метаданных
Изначально планировалось реализовать модуль парсинга сгенерированного `.gcode` файла для извлечения данных о времени печати и расходе пластика (необходимых для расчета стоимости). Однако изучение ответов `orca-slicer-api` показало, что API уже возвращает эти метаданные в JSON вместе с G-code. От кастомного парсера отказались, что упростило код и снизило нагрузку на диск.

#### Шаг 4. Выбор технологического стека и модели конкурентности
В качестве базы для воркера выбран **Python + FastAPI** (для унификации с остальными сервисами проекта и обеспечения `/health` эндпоинтов для оркестратора).

**Обоснование синхронных библиотек:**
Поскольку процесс нарезки — это длительная блокирующая операция (от нескольких до десятков минут), а воркер обрабатывает строго одну задачу за раз (`prefetch_count=1`), использование асинхронных библиотек не дает прироста производительности, но усложняет код. Было решено использовать **синхронные библиотеки**: `requests` (HTTP), `pika` (RabbitMQ) и `minio`.

**Реализация:**
Чтобы длительный синхронный HTTP-запрос к слайсеру не заблокировал Event Loop фреймворка FastAPI (что привело бы к зависанию health-чеков и убийству контейнера докером), слушатель RabbitMQ запускается в изолированном **фоновом потоке (threading.Thread)** при старте приложения.

#### Шаг 5. Структура проекта и разделение ответственности
Для обеспечения читаемости, легкости тестирования и поддержки, код воркера был спроектирован c жестким разделением слоев:

*   **`src/main.py`** — Точка входа (FastAPI). Отвечает за инициализацию приложения, запуск фонового потока для RabbitMQ и предоставление эндпоинта `/health`.
*   **`src/core/processor.py`** — основная логика воркера. Содержит функцию `process_slicing_task`, которая оркестрирует весь жизненный цикл (скачивание $\rightarrow$ нарезка $\rightarrow$ загрузка $\rightarrow$ отправка ответа) и гарантирует очистку временных файлов через блок `finally`.
*   **`src/core/config.py`** — Управление конфигурацией и переменными окружения через `pydantic-settings`.
*   **`src/clients/` (Внешние интеграции):** Инфраструктурный слой изолирован в трех адаптерах:
    *   `minio_client.py` — Инкапсулирует работу с S3 (скачивание/загрузка объектов).
    *   `orca_client.py` — Оборачивает HTTP-запросы `multipart/form-data` к API-слайсеру.
    *   `rabbit_client.py` — Скрывает логику работы с AMQP (pika), настройку `prefetch`, механизм ретраев и подтверждение/отклонение сообщений.
*   **`src/schemas/` (Контракты):** Pydantic-модели (`events.py`), повторяющие структуру AsyncAPI-контракта для валидации входящих/исходящих сообщений.
*   **`temp/`** — Эфемерная директория на жестком диске для кратковременного хранения STL-моделей и G-code.


#### Шаг 6. Unit-тестирование
Для проверки корректности работы сервиса без разворачивания реальной инфраструктуры реализовано модульное тестирование с помощью `pytest` и `unittest.mock`. Тестами покрыты три критических узла системы: бизнес-логика оркестратора, механизмы доставки сообщений и мониторинг состояния контейнера.

*1. Тестирование основного пайплайна (Бизнес-логика)**
*   **Сценарий успеха:** Проверяет, что при корректном запросе воркер скачивает нужные файлы, передает их в слайсер, загружает G-code в S3 и отправляет в RabbitMQ валидный `SliceCompletedEvent`.
*   **Изоляция сбоев:** Если `orca-slicer-api` возвращает ошибку, воркер перехватывает ее и формирует `SliceFailedEvent`, предотвращая зависание системы.
*   **Валидация контрактов:** Проверено, что Pydantic мгновенно отбрасывает невалидные JSON-запросы (`ValidationError`), экономя ресурсы сети и диска.

*2. Сетевая устойчивость (RabbitMQ Client)**
Так как работа с брокером очередей подвержена сетевым сбоям, реализованы тесты механизма обработки сообщений (`handle_consumer_message`):
*   **Защита от "ядовитых" сообщений (Poison Pills):** Если при обработке задачи возникает фатальная или логическая ошибка (например, неверный формат), сообщение отклоняется **без возврата в очередь** (`requeue=False`). Это защищает воркер от бесконечного цикла падений.
*   **Обработка веменных сбоев:** При проблемах с публикацией результата (например, обрыв связи) срабатывает механизм повторных попыток (`publish_event_with_retries`). Если лимит исчерпан, выбрасывается `RequeueMessageError`, и исходная задача возвращается в очередь (`requeue=True`) для обработки другим воркером.
*   **Подтверждение (Ack):** При успешном прохождении пайплайна сообщение корректно удаляется из очереди (`ch.basic_ack`).

*3. Мониторинг состояния**
Docker необходимо знать, жив ли контейнер. Написаны тесты для эндпоинта `/health`, гарантирующие, что воркер сообщает правду о своем состоянии:
*   **Проверка брокера:** Тест `check_broker_reachable` удостоверяется, что health-check не просто возвращает HTTP 200, а реально проверяет доступность RabbitMQ (открывает сокет, проверяет наличие очереди и закрывает соединение).
*   **Реакция на отказы:** Если брокер недоступен, эндпоинт отдает HTTP 503 `{"status": "unhealthy"}`, что дает сигнал не отправлять сюда трафик.
*   **Защита памяти:** Добавлен тест, гарантирующий, что если брокер вернет аномально длинное сообщение об ошибке, оно будет усечено до 500 символов.

**Итог:** Спроектирована надежная, легко масштабируемая архитектура воркера с четким разделением зон ответственности между микросервисами.
